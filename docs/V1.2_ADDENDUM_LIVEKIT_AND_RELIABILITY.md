# TRIPWIRE — v1.2 Addendum: LiveKit Integration & Reliability Fixes

This is an **addendum to the locked `docs/PRD.md` (v1.1)**, not a replacement. Everything in v1.1 still holds — the five pipeline invariants (`skills/tripwire-pipeline/SKILL.md`), the four-state sentence verdict, the fresh-per-sentence retrieval rule — none of that changes. This document adds four things on top of an already ~80-85% complete build, in strict priority order because remaining time is short:

**Architecture-preservation guarantee, since the app is already mostly built:** every item below is designed as an *addition* to the existing pipeline, not a rework of it. Item 1 (LiveKit) only ever produces a text string that enters the pipeline at the exact point typed text already enters it today — no change to sentence detection, retrieval, or verdict logic. Item 2 (Redis) swaps *where* session state lives, not its shape — same fields, same access pattern, just read/written through a key instead of an in-memory object. Item 3 (prompts) is text-only changes inside existing prompt strings — no new call sites. Item 4 (observability) is additive logging/tracing wrapped *around* existing calls, not a change to what those calls do. If any of the four ends up requiring you to touch verify-pipeline logic itself, stop and reconsider the approach — that's a signal you've drifted from the addendum's intent.

**Scope note on the full review vs. this addendum:** the fuller evaluation you received also lists generic "industry expects" items — GDPR consent/erasure, EEOC bias monitoring, JWT/OAuth2 auth, rate limiting, input-injection hardening. None of these appear in the actual scored **Recommendations** section (only the four below do), so they're deliberately left out of this addendum. Chasing them now would spend remaining time on unscored work while the one item that risks disqualification (LiveKit) is still open — don't.

## 1. LiveKit Voice Integration

### The core design decision

LiveKit becomes a **second front door into the exact same backend pipeline** — it does not replace anything, and it does not require touching the verification logic (steps 6-11 in `docs/APP_FLOW.md`'s state machine) at all. This is deliberate: the highest-risk thing you could do right now is let LiveKit's addition destabilize a pipeline that's already 80-85% working.

```
EXISTING (Text Mode, unchanged):
  Typed question → /api/generate → token stream → sentence detection →
  verify pipeline → UI

NEW (Voice Mode, additive):
  Spoken question → LiveKit room → LiveKit Agent (STT) → transcript
  finalized → SAME /api/generate → SAME token stream → SAME sentence
  detection → SAME verify pipeline → UI (+ optional spoken response)
```

The user picks Text Mode or Voice Mode per turn; both write into the same `qaTurns` array (per the PRD's multi-turn model) so the UI doesn't need two separate display paths.

### Two tiers — build Tier A first, only attempt Tier B if Tier A is solid with time to spare

**Tier A (do this — satisfies the mandate honestly):** the judge speaks their question instead of typing it. A LiveKit Agent worker joins a room, runs speech-to-text on the incoming audio, and once the transcript is finalized (LiveKit's STT plugins emit interim + final transcript events — wait for `is_final: true`), that final text string is passed into the existing `/api/generate` call exactly as if it had been typed. Everything downstream is untouched.

**Tier B (stretch goal, literal match to "verifying streaming audio transcriptions on-the-fly"):** instead of just transcribing a question, the LiveKit Agent itself is a voice conversational agent — it speaks an answer back (TTS), and its own spoken answer's transcript is fed sentence-by-sentence into the *existing* verify pipeline live, the same way the typed-answer token stream is today. This is architecturally almost identical to Tier A's plumbing (transcript events → sentence detector → verify pipeline) but adds a TTS leg and a persistent conversational agent loop. Only attempt this if Tier A works end-to-end with real time left over — it's a better demo, but Tier A alone is enough to satisfy "LiveKit is integrated and handles real-time voice-based queries."

### The deployment gotcha — read this before writing any code

**A LiveKit Agent worker is a long-running process that holds a persistent connection to the LiveKit server. It cannot run inside a Vercel serverless function** (which spins up per-request and has no persistent state or long-lived socket). This means:

- The Next.js app (everything already built) keeps deploying to Vercel exactly as planned.
- The LiveKit Agent worker is a **separate process** that needs a host that stays running: Render, Railway, Fly.io, a small persistent VM, or LiveKit Cloud's own agent-hosting option if available on your plan.
- For the actual judged demo, if hosting a second service under time pressure is too risky, running the Agent worker on your own laptop during the live demo is an accepted fallback for a hackathon — but if the "Deployed Link" submission requirement is evaluated asynchronously (a judge trying it without you present), the worker needs to actually be hosted somewhere reachable, not just runnable locally. Decide which situation you're in and plan accordingly; don't discover this the night before submission.

### Concrete build tasks

1. Create a LiveKit Cloud project (or self-hosted server if you already have one) — get `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`.
2. Add a "Voice" toggle next to the existing text input in the Screen 2 question bar (see `docs/APP_FLOW.md`).
3. On selecting Voice mode: client requests a LiveKit access token from a new `/api/livekit-token` route, joins the room, and starts publishing the mic track.
4. Build the Agent worker (LiveKit's Agents framework, Node.js or Python — pick whichever your existing stack makes easier to wire in; the framework is language-flexible) with an STT plugin. Any plugin with a workable free/trial tier is fine — the specific choice doesn't affect the rest of the architecture, so don't spend time comparing providers if one has a working key already.
5. On a final transcript event, the Agent (or the Next.js backend, listening via a webhook/data channel) calls the existing `/api/generate` route with that text as the question, exactly as the text-input path already does.
6. New environment variables go in `.env.example`: `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, plus whatever key your chosen STT plugin needs.
7. Add this as **FR-13** in the PRD when you have a moment: "Voice question input via LiveKit, transcribed and passed into the existing generation pipeline unchanged."

## 2. Externalize Session State (Redis via Upstash)

### Why this is likely a real bug, not just a scoring nitpick

The current design (PRD Section 10.3) holds session state — `documentMeta`, `chunks`, `qaTurns` — in server-side memory for the life of a session. On Vercel, each API route invocation can land on a **different serverless instance** with its own memory. If a document gets indexed on one invocation and the next question's API call lands on a different instance, that instance has never heard of the session — this can silently break exactly the kind of multi-turn flow your v1.1 PRD fix was designed to support.

### The fix

Move session state into **Upstash Redis** (REST-based, works from serverless/edge, generous free tier, no persistent server to manage — this is not the "add a database" you were told to avoid; it's an ephemeral cache with a TTL, philosophically the same as in-memory state, just shared correctly across invocations).

- Generate a `sessionId` client-side on first document upload (a UUID), store it in a cookie or pass it explicitly with every request.
- Redis key: `session:{sessionId}` → a JSON blob containing `documentMeta` and `qaTurns`. **Don't duplicate chunk text into Redis** — Moss already stores it; keep only `chunkId`/`mossVectorId` references in the session blob to keep it small.
- Set a TTL (e.g., 2 hours) on the key so it behaves like ephemeral session memory, not permanent storage — this preserves the "no database" spirit of the original architecture decision while fixing the actual cross-invocation bug.
- Every API route (`/api/session`, `/api/generate`, `/api/verify`) reads/writes through this Redis key instead of an in-memory object.

New environment variables: `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`.

## 3. Prompt Restructuring — CRISPE + Few-Shot

Restructure the three existing LLM prompts (generation, verdict, explanation — FR-4/FR-8/FR-10) using **C**ontext, **R**ole, **I**nstruction, **S**pecifics, **P**ersonality, **E**xperiment. Below is the full restructured text for each — these are meant to be copied close to verbatim into the actual prompt strings in code.

### 3a. Verdict classification prompt (FR-8) — the one that matters most

This is the prompt where a mistake is highest-cost (Invariant 1 in `skills/tripwire-pipeline/SKILL.md`), so it gets the full few-shot treatment using the same test pairs already required by the PRD's FR-8 acceptance criteria.

```
[Context]
You are checking a single sentence, generated by another AI answering a
question about a document, against passages retrieved from that same
document. Your judgment will be shown live to a person as a trust signal
about the AI's answer.

[Role]
You are a strict fact-verification classifier. You are not being asked
whether the sentence is well-written, relevant, or reasonable — only
whether the source passages support it, contradict it, or say nothing
either way.

[Instruction]
Given the SENTENCE and the three RETRIEVED PASSAGES below, respond with
exactly one word: SUPPORTED, CONTRADICTED, or UNVERIFIABLE. Do not explain
your answer. Do not respond with anything else.

[Specifics]
- SUPPORTED: at least one passage confirms the sentence's claim, including
  matching numbers, dates, named entities, and direction (increased vs.
  decreased, rose vs. fell).
- CONTRADICTED: a passage addresses the same claim but with a different
  number, date, entity, or opposite direction/negation. A passage that is
  topically similar but flips a number or direction word is CONTRADICTED,
  not SUPPORTED — similarity is not agreement.
- UNVERIFIABLE: no passage addresses this specific claim, even if the
  general topic is related.

[Personality]
Be strict and literal. When genuinely torn between SUPPORTED and
UNVERIFIABLE, choose UNVERIFIABLE — an unnecessary caution is far less
costly than a wrong confirmation.

[Experiment — few-shot examples]
Example 1
SENTENCE: "Operating costs decreased 30% from last year."
PASSAGE: "Operating costs rose 8% year-over-year due to increased hiring."
ANSWER: CONTRADICTED

Example 2
SENTENCE: "Revenue increased 10% to $45 million in Q3."
PASSAGE: "Q3 revenue grew 10% year-over-year to $45M."
ANSWER: SUPPORTED

Example 3
SENTENCE: "The company opened three new offices in Europe this year."
PASSAGE: "The company's headcount grew by 200 employees in Q3."
ANSWER: UNVERIFIABLE

Example 4
SENTENCE: "Customer churn dropped to 4% this quarter."
PASSAGE: "Churn increased slightly to 6.2% in Q3, up from 5.8% the prior
quarter."
ANSWER: CONTRADICTED

Example 5
SENTENCE: "The product launched in 12 countries."
PASSAGE: "The product is now available in 12 markets across Europe and
Asia."
ANSWER: SUPPORTED

---
SENTENCE: {sentence}
PASSAGE 1: {passage_1}
PASSAGE 2: {passage_2}
PASSAGE 3: {passage_3}
ANSWER:
```

Note: this reuses/extends the exact pairs your PRD's FR-8 acceptance criteria already required you to test against (5 direction-flip + 5 number-change pairs) — write the remaining 5 the same way and rotate through all 10 as your regression set even though only 5 are shown here as in-prompt examples (too many examples inflates the prompt and slows the call; 5 well-chosen ones is enough signal).

### 3b. Generation prompt (FR-4)

```
[Context]
You are answering a user's question using only the document provided
below as your source of truth. Your answer will be verified sentence-by-
sentence against this same document by a separate system, so accuracy
matters more than completeness.

[Role]
You are a careful analyst summarizing or answering questions strictly
from the provided source material.

[Instruction]
Answer the QUESTION using only information in the DOCUMENT. Write in
clear, complete sentences. Do not add information the document doesn't
contain.

[Specifics]
- If the document doesn't address part of the question, say so explicitly
  rather than inferring or guessing.
- Prefer precise numbers, dates, and direction words exactly as stated in
  the document over paraphrased or rounded versions.

[Personality]
Neutral, factual, concise. No filler sentences like "This is an
interesting question" — every sentence should carry either an answer or
an explicit statement that the document doesn't cover something.

DOCUMENT:
{document_text}

QUESTION:
{question}
```

### 3c. Explanation prompt (FR-10)

```
[Context]
A sentence in a generated answer has been flagged as CONTRADICTED or
UNVERIFIABLE against a source passage. A person is looking at this flag
and needs a one-line reason, not a full analysis.

[Role]
You are writing a single, plain-language explanation line shown directly
under a flagged sentence in a live UI.

[Instruction]
In one short sentence, state what the source passage actually says versus
what the flagged sentence claims. If UNVERIFIABLE, state that no passage
addresses this specific claim.

[Specifics]
Maximum one sentence. No preamble ("Looking at this, I can see..."). Lead
directly with the source's actual content.

[Personality]
Plain and direct, like a fact-checker's caption, not a chatbot.

SENTENCE: {sentence}
VERDICT: {verdict}
MATCHED PASSAGE(S): {passages}

EXPLANATION:
```

## 4. LLM Observability — Minimal Viable Version First

The review specifically names **OpenTelemetry** as the expected instrumentation layer, so both the minimal and stretch versions below are structured around OTel's concepts (spans, trace context) even where the minimal version doesn't pull in the full SDK — this makes upgrading from "structured logs" to "real OTel" later a matter of wiring, not a redesign.

### Do this much regardless of remaining time (low effort, answers the core complaint)

Add a `traceId` — reuse the existing `turnId` from the `qaTurns` model, it already uniquely identifies one question-answer turn — and propagate it through every downstream call. At each stage (Moss retrieval, verdict call, explanation call), emit one structured JSON log line shaped like an OTel span (so it's a straightforward upgrade later, not a rewrite):

```json
{
  "traceId": "<turnId>",
  "spanName": "verdict_classification",
  "sentenceId": "...",
  "durationMs": 187,
  "tokensIn": 412,
  "tokensOut": 3,
  "promptHash": "<sha256 of the prompt TEMPLATE, not the filled content>",
  "timestamp": "..."
}
```

**Important:** hash the prompt *template* (the CRISPE structure above), not the filled-in content — the filled content contains the judge's own uploaded document text, which you should not be logging verbatim into any log stream, your own or a third party's.

This alone, viewable in Vercel's function logs, directly answers "complete absence of tracing, token tracking, correlation IDs" — because it no longer is absent.

### Stretch, only if time remains: wire a real observability platform

**LangSmith** is the lower-lift option here — it wraps OpenAI-compatible calls with minimal code change and has a workable free tier, which matters given how little time is left. **Arize Phoenix** is a legitimate alternative and fully open-source, and notably ships native **OpenTelemetry** instrumentation out of the box (it's built on the OTel spec directly) — if you want to be able to say "instrumented with OpenTelemetry" literally rather than "OTel-shaped logging," Phoenix is the more literal match to the review's wording, at the cost of needing a hosted instance (self-run or their cloud), which is more setup than is worth it unless items 1-3 above are already done with real time to spare.

If you get to this: wrap the three LLM call sites (generation, verdict, explanation) and the Moss retrieval call with spans tagged by the same `traceId`/`turnId`, using the OTel SDK's `tracer.startSpan()`/`span.end()` pattern (both LangSmith and Phoenix can consume standard OTel spans), so a single question-turn's full trace — retrieval latency, verdict latency, token counts, all of it — is viewable as one connected trace rather than scattered log lines.

## What NOT to do under this addendum

- Do not remove or restructure the existing text-input path — voice is additive.
- Do not let LiveKit integration touch the sentence-detection or verify-pipeline code at all — it should only ever produce a text string that enters the pipeline exactly where typed text already does.
- Do not add Redis as a place to log full document content or full prompts — it's for session *pointers* (chunk IDs, turn text), not a document store.
- Do not start the observability platform integration before LiveKit (item 1) is working — priority order at the top of this document is not a suggestion.
